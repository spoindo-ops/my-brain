### 🛠️ `pack_apply.py` 실패 로그 최종 분석 및 수정 계획

#### 1. 실패 원인 진단 (Diagnosis)
이전 로그 분석 결과, 주요 실패 지점은 다음과 같이 추정되며, 이는 주로 **외부 API 호출의 불안정성**과 **파일/데이터 상태 관리의 비동기 문제**에서 기인합니다.

*   **원인 A: 외부 서비스 의존성 오류 (API Failure)**
    *   특정 단계에서 외부 서비스(예: 결제 시스템, 데이터베이스)와의 통신이 예상치 못한 응답 시간 초과나 잘못된 JSON 구조로 인해 실패했습니다. 이는 `pack_apply.py` 내의 API 통합 로직(`web_init`, `web_preview` 등)에 직접적인 영향을 미칩니다.
*   **원인 B: 데이터 무결성 불일치 (Data Inconsistency)**
    *   자동화 과정에서 중간 결과물(예: 디자인 적용, 파일 생성)이 예상과 다르게 저장되거나, 이전 단계의 성공 여부가 다음 단계로 올바르게 전달되지 않아 후속 작업이 실패했습니다. 이는 `Visual Asset` 또는 `SignOffChecklist` 데이터와 실제 파일 시스템 상태 간의 동기화 문제에서 발생합니다.
*   **원인 C: 비동기 흐름 관리 미흡 (Asynchronous Flow Management)**
    *   여러 병렬 프로세스(파일 처리, API 호출)가 동시에 진행될 때, 각 프로세스의 상태를 정확히 추적하고 오류 발생 시 적절한 롤백 또는 재시도 메커니즘이 부족하여 시스템 전체의 안정성이 저하되었습니다.

#### 2. 구체적인 수정 계획 (Modification Plan)
안정성을 확보하기 위해 다음 세 가지 핵심 영역에 대한 수정을 제안합니다.

**A. API 통합 계층 강화 (Robust API Layer)**
*   **수정 목표:** 외부 API 호출 실패에 대한 탄력성(Resilience)을 높입니다.
*   **액션 1: 재시도 로직 구현 (Retry Mechanism)**
    *   모든 외부 API 호출 함수(`web_init`, `web_preview` 등)에 **Exponential Backoff** 기반의 자동 재시도 로직을 적용합니다. 최대 N회 실패 시 명확한 에러를 반환하도록 설정합니다.
*   **액션 2: 입력/출력 유효성 검사 강화 (Input/Output Validation)**
    *   API 응답(JSON) 수신 후, Pydantic 모델 또는 정의된 스키마에 대한 엄격한 검증을 추가하여 잘못된 데이터가 파이프라인으로 유입되는 것을 원천 차단합니다.

**B. 데이터 무결성 보장 (Data Integrity Enforcement)**
*   **수정 목표:** 파일 시스템 상태와 데이터베이스 상태 간의 일관성을 강제합니다.
*   **액션 3: 트랜잭션 기반 작업 분리 (Transactional Job Separation)**
    *   각 자동화 단계를 독립적인 트랜잭션 단위로 묶습니다. 한 단계가 실패하면, 해당 단계에서 생성된 임시 파일이나 DB 기록은 **Rollback**되도록 설계합니다.
*   **액션 4: 상태 플래그 도입 (State Flag Introduction)**
    *   `pack_apply.py` 실행 전후에 모든 중요한 상태(예: `asset_applied`, `qa_passed`)를 명시적으로 DB/파일에 기록하는 플래그를 추가하여, 다음 실행 시 어떤 부분이 완료되었는지 명확히 추적합니다.

**C. 에러 핸들링 및 로깅 개선 (Error Handling & Logging)**
*   **수정 목표:** 실패 발생 시 디버깅을 용이하게 하고 사용자에게 명확한 피드백을 제공합니다.
*   **액션 5: 상세 오류 기록 (Detailed Error Logging)**
    *   단순히 `Exception`을 던지는 것을 넘어, **실패 지점(Line Number), 입력 데이터, 실패 원인(HTTP Status Code, 상세 메시지)**을 포함하는 구조화된 로그를 생성하도록 수정합니다.
