## 🛠️ 2. 테스트 시나리오 분류 및 상세 계획

### A. [✅ Success Case] 기본 성공 경로 테스트 (Happy Path)
| ID | 목적 | 전제 조건 / 입력 데이터 | 기대 결과 | 검증 항목 |
| :--- | :--- | :--- | :--- | :--- |
| SC-001 | 모든 필드 정상 유효성 및 통합 확인 | 스키마의 모든 필수 필드를 완벽하게 포함한 데이터. (PPM, CO2e, GPS 모두 값 존재) | HTTP 200 OK. 데이터 처리 완료 성공 응답 코드 반환. | 전송된 모든 데이터가 정확히 DB에 기록되는지 검증. |
| SC-002 | Enum 필드 유효성 테스트 | `source_method`를 정의된 Enum 값 ([Farm, Lab, Wild])으로만 입력. | HTTP 200 OK. 성공적으로 로직 통과. | 외부/잘못된 Enum 값이 거부되는지 확인 (Failure Path와 연계). |

### B. [⚠️ Warning State] 경고 상태 테스트 (Critical Data Integrity Check)
**목적:** 데이터가 필수적이지 않거나, 시스템이 처리할 수 있지만 '수동 검토 필요'한 임계치 근처의 값을 테스트합니다. 이 케이스는 4xx 에러를 반환하지 않고, `202 Accepted`와 같은 응답 코드를 반환하며 본문(Body)에 경고 플래그(`warning_flags`)를 포함해야 합니다.

| ID | 시나리오 (문제점) | 입력 데이터 예시 | 기대 결과 (응답 코드: 202) | 처리 스크립트 요구 사항 |
| :--- | :--- | :--- | :--- | :--- |
| WS-001 | **PPM 임계치 초과** | `purity_ppm`: 최대 허용 농도보다 높은 값. (예: 95%) | 경고 플래그 포함 응답. (`"warning": "PPM 값이 규제 상한을 초과했습니다."`) | 후처리 스크립트에서 해당 배치를 '수동 검토 대기' 테이블로 자동 분류하고 알림 발송 로직 추가. |
| WS-002 | **CO2e 데이터 누락** | `carbon_footprint`: 0 또는 Null 값으로 전송 (필수는 아니나, 추정 필요). | 경고 플래그 포함 응답. (`"warning": "탄소 배출량 데이터가 불명확합니다."`) | 시스템이 과거 유사 배치 데이터를 기반으로 **추정값(Estimated Value)**을 계산하여 임시로 삽입하고, 이 값을 명시해야 함. |
| WS-003 | **위험 지역 경고** | `geo_location`의 좌표가 알려진 '규제 위험 지역' (예: 특정 해역)과 일치하는 경우. | 경고 플래그 포함 응답. (`"warning": "해당 위치는 규제 리스크가 높은 지역입니다."`) | 백엔드에서 지도 API와 연동하여 실시간으로 지리적 위험도를 체크하고, 점수화(Risk Score) 필드를 추가해야 함. |

### C. [❌ Failure State] 치명 오류 테스트 (Negative Path)
**목적:** 시스템이 절대 처리할 수 없는 비정상적인 입력값을 보내어 게이트웨이가 정상적으로 실패를 감지하고 사용자에게 구체적인 에러 코드를 반환하는지 검증합니다.

| ID | 시나리오 (문제점) | 입력 데이터 예시 | 기대 결과 (응답 코드: 400/422) | 디버깅 및 처리 스크립트 요구 사항 |
| :--- | :--- | :--- | :--- | :--- |
| FS-001 | **필수 필드 누락** | `batch_uuid` 또는 `collection_date` 등 필수 필드 중 하나가 아예 빠진 경우. | HTTP 400 Bad Request. 누락된 필드의 이름과 타입을 명시한 에러 메시지 반환. | API Gateway 레벨에서 **스키마 유효성 검사 (Schema Validation)**를 통해 즉시 차단(Fail Fast). |
| FS-002 | **데이터 타입 불일치** | `purity_ppm`에 문자열("N/A")이 들어간 경우. | HTTP 422 Unprocessable Entity. 기대 데이터 타입과 실제 받은 타입을 명시한 오류 반환. | 모든 입력 필드는 Pydantic 모델을 사용하여 강제 검증(Type Casting)해야 하며, 실패 시 상세 스택 트레이스를 로깅하도록 구성. |
| FS-003 | **UUID 포맷 위반** | `batch_uuid`에 유효하지 않은 문자열이 들어간 경우. | HTTP 422 Unprocessable Entity. UUID 포맷 오류를 구체적으로 안내. | 입력값 정규식(Regex) 검증을 통해 최소한의 포맷 구조만 통과시키고, 상세 검사는 서비스 로직에서 처리하는 계층 분리 필요. |

## ⚙️ 3. 통합 개발/테스트 환경 요구 사항
1.  **Validation Layer:** 모든 요청은 **FastAPI + Pydantic Model**을 사용하여 스키마 유효성(FS-001, FS-002)을 먼저 검증해야 합니다.
2.  **Middleware Layer (Gateway):** 게이트웨이는 1차적으로 필수 필드 검증 후, Warning State 체크 로직 (WS-001, WS-003)을 실행하고, 결과에 따라 최종 응답 상태(200 vs 202)를 결정해야 합니다.
3.  **Logging:** 모든 경고 및 오류 상황은 `log_level=WARN` 또는 `ERROR`로 기록되며, 해당 배치의 UUID와 문제 필드를 명시하여 추후 재처리(Re-run/Retry)가 가능하도록 로깅 시스템을 구축합니다.
